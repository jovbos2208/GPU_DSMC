# Benchmarks (M5.1 – M5.5, M6.7)

Performance baseline, profiles and before/after measurements of the M5
optimisations. Raw results: `results/*.json` (written by
`scripts/benchmark.py`, one file per build and label).

## Cases

| Case | Solver | Content | Run length |
| ---- | ------ | ------- | ---------- |
| B1 | TPMC | example satellite (`examples/geometry/satellite.stl`), VLEO air O/N2/O2/N/He, CLL | 2·10⁷ histories |
| B2 | TPMC | sphere with 65 024 triangles (BVH load), O, Maxwell | 10⁷ histories |
| B3 | DSMC | 0.5 m cube, He, Kn ≈ 1, Δx = 0.05 m, Δt = 2 µs, 30 particles/cell | 200 + 1000 steps |
| B4 | DSMC | satellite, O/N2/O2 (rotation, vibration), Kn ≈ 0.5, Δx = 0.1 m | 200 + 600 steps |

The configurations are generated by the script (fixed seeds) and cover the
dominant work types: BVH traversal with few or many triangles (B1, B2), and
the DSMC time step with monatomic gas and with internal energy (B3, B4).

```bash
python3 scripts/benchmark.py run build/<preset>/vleo_solver <label> [--repeat 3] [--cases B1 B3]
python3 scripts/benchmark.py compare results/<before>.json results/<after>.json
```

Each case is run `--repeat` times; the median wall time is reported together
with the throughput (histories/s, DSMC particle steps/s), the phase profile
(`--profile`: each phase is fenced, so the sum is the wall time of the
measured loop) and the **efficiency** SE(C_D)² · wall time (time for a given
statistical accuracy; lower is better, independent of the run length).

## Method for before/after comparisons (M5.4)

The development laptop is not quiet (desktop load average 7–11), so
sequential runs fluctuate by up to ±15 %. The final comparison therefore
uses a separate build of the M4 state (commit `27b4990`, `git worktree`) and
the M5 build, run directly after each other, three repetitions each, median.
Repetitions of one build agree within 1 % on the GPU and 3–9 % on the CPU.
After every optimisation step the complete test suite was run and
`C_D` was compared: **all results are bitwise identical** to the M4 build
(same seed and backend, z = 0.0 in every row below).

## Optimisations (M5.3, M5.5)

| Step | Change | Effect | Kept |
| ---- | ------ | ------ | ---- |
| opt1 | DSMC: lazy compaction – ended particles stay as `Free` slots until more than 5 % of the storage is free; non-active particles skip binning | CPU B3/B4: compaction share 27 % → ~3 % | yes |
| opt2 | DSMC: cell sort compares storage indices instead of loading particle ids (ids grow with the index, invariant tested in `test_grid`) | CPU sort −30 % | yes |
| opt3 | DSMC: non-sampling steps reduce only status counts and interactions (one reduction instead of the full moment set); value count = actual species | step reduce −40 % | yes |
| opt3 | TPMC: fused inject + transport kernel (no particle arrays written between the two) | CPU B1 +8 %; **GPU slower** (register pressure, −10 %) | host backends only |
| opt4 (M5.5) | BVH node boxes in single precision (outward-rounded with `nextafter` and padded by 1e-5 × geometry scale; ray–triangle tests stay in double) | GPU B2 +24 %; CPU −5 % | GPU backends only (`BvhReal`) |

Mixed precision (M5.5), error analysis: a float box is only used for culling.
The stored box contains the exact double box (padding ≥ 1e-5 · scale is
far larger than float rounding of ≤ 6e-8 · scale, plus outward rounding), so
no ray that hits a triangle in double precision can be culled: the closest hit
and the crossing count are exactly those of the double BVH. Verified by the
brute-force comparison tests in `test_ray`/`test_transport` on GPU and by
the bitwise identical benchmark results. Larger boxes only cost extra node
visits, which is the reason for the slowdown on CPUs (no gain from float
loads there).

## Result: M4 → M5 (median of 3, interleaved builds, 2026-11-13)

CPU, `cpu-release`, 12 threads (`ab-base-cpu.json` → `ab-m5-cpu.json`):

| ---- | ------ | ------ | ------------- | -------- | --------------- |
| B1 | 1.80 | 1.64 | 1.22·10⁷ histories/s | 1.10× | 4.95440 |
| B2 | 3.29 | 2.91 | 3.44·10⁶ histories/s | 1.13× | 1.65450 |
| B3 | 15.32 | 11.71 | 1.85·10⁷ particle steps/s | 1.31× | 0.71228 |
| B4 | 20.42 | 16.51 | 1.74·10⁷ particle steps/s | 1.24× | 4.61274 |

GPU, `hip-gfx1103`, Radeon 740M (`ab-base-hip-gfx1103.json` → `ab-m5-hip-gfx1103.json`):

| Case | M4 [s] | M5 [s] | Throughput M5 | Speed-up | C_D (identical) |
| ---- | ------ | ------ | ------------- | -------- | --------------- |
| B1 | 3.96 | 3.88 | 5.16·10⁶ histories/s | 1.02× | 4.95440 |
| B2 | 5.54 | 3.86 | 2.59·10⁶ histories/s | 1.44× | 1.65450 |
| B3 | 17.41 | 16.59 | 1.31·10⁷ particle steps/s | 1.05× | 0.71246 |
| B4 | 30.30 | 26.17 | 1.10·10⁷ particle steps/s | 1.16× | 4.61486 |

The M5 runs include `--profile` (fences after every phase), so the M5 times
are slightly pessimistic. In quiet conditions, single CPU runs reached up to
2.0× (B3) and 1.7× (B4), because the M4 compaction cost grows with
memory-bandwidth contention. The CPU and GPU C_D differ in the last digits
because floating-point rounding (device math, reduction order) changes
individual DSMC collisions; TPMC is identical across backends.

Profiles after M5: the GPU DSMC step is dominated by the move kernel
(45–53 %) and collisions (20–39 %); on the CPU by move (41–47 %). Further
work (not done): per-cell particle reordering for coalesced access in the
move/collide kernels, and a shared-memory traversal stack for the BVH.

The intermediate files `opt1-cpu` … `opt4-*` are the sequential
measurements of the individual steps (noisy, see above).

## Dedicated GPU: Radeon PRO W7700 (2026-11-13, M5 state `69eb66c`)

Median of 3 (`m5-hip-gfx1101`, run on the server):

| Case | Wall [s] | Throughput | vs. 740M iGPU | vs. 12-thread CPU | C_D |
| ---- | -------- | ---------- | ------------- | ----------------- | --- |
| B1 | 0.32 | 6.34·10⁷ histories/s | 12× | 5.1× | 4.95440 |
| B2 | 0.26 | 3.92·10⁷ histories/s | 15× | 11× | 1.65450 |
| B3 | 6.10 | 3.56·10⁷ particle steps/s | 2.7× | 1.9× | 0.71246 |
| B4 | 6.73 | 4.26·10⁷ particle steps/s | 3.9× | 2.5× | 4.61486 |

C_D is bitwise identical to the Radeon 740M (gfx1103) build – same code, same
seeds, different GPU generation and HIP version (6.3 vs. 7.1).

Profiles: TPMC transport 59–73 %, injection 22–35 %. DSMC was dominated by
the **cell sort** (B3 59 %, B4 28 %), followed by collisions (18 %, 51 %) and
move (9 %, 11 %). Cause: the sort was an insertion sort with one thread per
cell. On the iGPU the atomic fill delivers particles almost in index order
(few compute units), so the insertion sort is nearly O(n); on the W7700
with 48 CUs the order is close to random, the sort becomes O(n²) per cell and
serial, with only 4096 threads (B3 has 16³ cells).

**Follow-up optimisation (rank sort, GPU backends only):** the binning fills
an unsorted list, then one thread per particle counts the smaller entries of
its cell and writes itself to its final position (`RankSortEntries` in
`src/dsmc/Dsmc.cpp`). The result is the same sorted list (results bitwise
unchanged, all tests pass); the work no longer depends on the fill order and
uses one thread per particle. On the 740M it is neutral (`ranksort-hip-gfx1103`:
B3 15.5 s, B4 25.1 s vs. 16.6/26.2 s; the sort itself 0.9 s vs. 0.7 s
because the input was already nearly sorted there). On the W7700 (`m5-ranksort-hip-gfx1101`, server run, median of 3):

| Case | insertion sort [s] | rank sort [s] | Speed-up | sort share | C_D (identical) |
| ---- | ------------------ | ------------- | -------- | ---------- | --------------- |
| B3 | 6.10 | **2.75** | 2.2× | 59 % → 5 % | 0.71246 |
| B4 | 6.73 | **5.12** | 1.31× | 28 % → 2 % | 4.61486 |

B3 now runs at 7.9·10⁷ particle steps/s (4.3× the 12-thread CPU, 5.6× the
iGPU), B4 at 5.6·10⁷ (3.2× CPU). TPMC unchanged (B1 0.32 s, B2 0.25 s).

New profile on the W7700: collisions 42 % (B3) and **69 % (B4)**, move
21 %/15 %, step reduce 12 %/6 %. The collision kernel has the same structure
as the old sort – one thread per cell, the NTC pairs of a cell are processed
sequentially – which is the next bottleneck on large GPUs. Parallelising
within a cell changes the order of the random numbers, so results stay
deterministic and statistically equivalent but are no longer bitwise equal to
the previous version.

**Wave-parallel collisions (GPU backends):** every candidate pair has its own
random stream and all candidates of a step use the bound from its start, so
the result no longer depends on a single serial random sequence. One team of
32 threads per cell processes the candidates in waves of independent pairs
(a candidate waits for all earlier ones sharing a particle) – bitwise
identical to the per-cell kernel used on host backends (`test_dsmc`), see
docs/dsmc.md §4. Results versus the previous version: statistically equal
(B3 z = 0.4, B4 z = 0.3; fixed-seed example references regenerated).

| Build | Case | before [s] | after [s] | collide before → after |
| ----- | ---- | ---------- | --------- | ---------------------- |
| cpu-release (interleaved, `headbase-cpu` → `waves-cpu`) | B3 | 13.95 | 13.34 (1.05×) | unchanged kernel structure |
| | B4 | 18.36 | 18.44 (1.00×) | |
| hip-gfx1103 (`ranksort-` → `waves-hip-gfx1103`) | B3 | 15.49 | 16.62 | 2.89 s → 2.13 s |
| | B4 | 25.09 | 26.74 | 9.01 s → 8.65 s |

On the 740M the collision kernel itself got faster; the slower totals come
from the unchanged move kernel (+16 %, desktop load during the run). On the W7700 (`m5-waves-hip-gfx1101`, server run, median of 3, all 52 tests
pass there):

| Case | M5 first run [s] | + rank sort [s] | + wave collisions [s] | total speed-up | collide share |
| ---- | ---------------- | --------------- | --------------------- | -------------- | ------------- |
| B3 | 6.10 | 2.75 | **2.21** | 2.8× | 42 % → 25 % |
| B4 | 6.73 | 5.12 | **3.52** | 1.9× | 69 % → 52 % |

B3: 9.8·10⁷ particle steps/s (6.0× the 12-thread CPU), B4: 8.2·10⁷
(5.2× CPU). C_D (0.71215, 4.61631) is bitwise identical to the 740M build of
the same version. Remaining profile on the W7700: B3 move 27 %, collide 25 %,
step reduce 16 %; B4 collide 52 %, move 23 %. Further candidates: team size
and chunk size of the wave kernel, the Larsen–Borgnakke branch divergence in
mixed N2/O2 cells, and fusing the step reduction into the move kernel.

## Several GPUs: 2× Radeon PRO W7700 (M6.7, 2026-11-16, `m6-mpi` at `6875868`)

Server `hagen`, preset `hip-gfx1101-mpi`, Open MPI 5.0.6, one rank per GPU
(`rank_device_ids [0, 1]`). Median of 3 runs, `--profile`:

```bash
python3 scripts/benchmark.py run $S w7700-mpi7-np1 --cases B1 B3 B4 B5
python3 scripts/benchmark.py run $S w7700-mpi7-np2 --cases B1 B3 B4 B5 --ranks 2
python3 scripts/benchmark.py run $S w7700-mpi7-np2-weak --cases B1 B5 --ranks 2 --scale 2
```

B5 is B4 with 0.05 m cells (8× the cells, 2.4 M particles), added to fill
two GPUs. It is not part of the default set. `--scale 2` doubles the
particles per cell (DSMC) or the histories (TPMC). C_D is identical for one
and two GPUs in every case (z = 0.0): this is the decomposition guarantee of
docs/parallel.md, here on GPUs.

**Strong scaling (same problem on 2 GPUs).** Wall time is the full run
(set-up, fill, time loop); "steps" is the fenced time loop only:

| Case | particles | wall 1 GPU [s] | wall 2 GPUs [s] | speed-up | steps 1 → 2 GPUs [s] | steps speed-up |
| ---- | --------- | -------------- | --------------- | -------- | -------------------- | -------------- |
| B1 TPMC | 2·10⁷ histories | 0.315 | 0.169 | **1.86×** | – | – |
| B3 DSMC | 0.18 M | 2.024 | 2.041 | 0.99× | 1.960 → 1.956 | 1.00× |
| B4 DSMC | 0.37 M | 2.967 | 2.602 | 1.14× | 2.897 → 2.531 | 1.14× |
| B5 DSMC | 2.4 M | 3.023 | 2.193 | **1.38×** | 2.782 → 1.949 | 1.43× |

**Weak scaling (twice the problem on 2 GPUs):**

| Case | throughput 1 GPU | throughput 2 GPUs | gain | efficiency |
| ---- | ---------------- | ----------------- | ---- | ---------- |
| B1 | 6.35·10⁷ histories/s | 1.22·10⁸ | 1.92× | 96 % |
| B5 | 2.34·10⁸ particle steps/s | 3.88·10⁸ | 1.66× | 83 % |

**Phases, B5 (rank 0, seconds per run):**

| Phase | 1 GPU | 2 GPUs | ratio |
| ----- | ----- | ------ | ----- |
| move | 1.165 | 0.595 | 1.96× |
| collide | 0.723 | 0.429 | 1.69× |
| step reduce | 0.402 | 0.363 | 1.11× |
| migrate (incl. MPI 0.121) | – | 0.314 | – |
| set-up | 0.189 | 0.103 | 1.8× |

Interpretation:

- **TPMC** scales almost ideally: histories are independent, and only the
  moments are exchanged once per batch.
- **DSMC** gains only once each GPU has enough work. Move and collisions
  scale. The costs per step that do not shrink with the problem size dominate
  small cases: the step reduction (an array reduction over all particles that
  only shrinks from 0.40 to 0.36 s here – cause not yet analysed) and the
  particle exchange (~1 ms per step: two
  device-to-host syncs, `MPI_Alltoall` + `MPI_Alltoallv` through host memory).
  For B3 (0.18 M particles, ~1.6 ms per step on one GPU) two GPUs bring no
  gain. Use one GPU per run for cases of that size.
- Rule of thumb from these runs: several GPUs pay off from roughly 10⁶
  particles per GPU (B5: 1.2 M per GPU, 1.43× in the time loop). Set-up and
  fill are paid once, so long runs come closer to the time-loop speed-up.

Optimisations made while measuring (all results unchanged; 1–4 ranks
identical counters, tests `mpi`):

| Step | B5, 2 GPUs [s] | change |
| ---- | -------------- | ------ |
| first multi-rank version | – (B4 1.08×) | per step: 2 `MPI_Allreduce`, buffer allocation, foreign-particle check |
| per-rank statistics summed once in `result()` (`e5a4a50`) | 3.27 (1.20×) | only the particle exchange is left per step |
| pinned staging buffers (`e4fcd19`) | 3.14 (1.25×) | |
| migrants recorded by the move kernel, direct pinned exchange, contiguous sort keys (`2f9574a`, `5a3a767`) | 3.09 (1.27×) | migrate 0.46 → 0.27 s; no scan over all particles |
| team-parallel cut-cell sampling (`6875868`) | **2.19 (1.38×)** | set-up 1.12 → 0.19 s on 1 GPU; also helps single-GPU runs |

Next candidates (not done): fuse the step reduction into the move kernel
(it does not scale and costs 13–19 % of the DSMC step on one GPU as well),
overlap the particle exchange with the binning of the resident particles,
and inject directly on the owning rank (injected particles are currently
spread over the ranks by index and migrate after their first move; their
share of the 12 000 migrants per step in B5 has not been measured).
