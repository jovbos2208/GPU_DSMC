# Benchmarks (M5.1 – M5.5)

Performance baseline, profiles and before/after measurements of the M5
optimisations. Raw results: `results/*.json` (written by
`scripts/benchmark.py`, one file per build and label).

## Cases

| Case | Solver | Content | Run length |
| ---- | ------ | ------- | ---------- |
| B1 | TPMC | example satellite (`examples/geometry/satellite.stl`), VLEO air O/N2/O2/N/He, CLL | 2·10⁷ histories |
| B2 | TPMC | sphere with 65 024 triangles (BVH load), O, Maxwell | 10⁷ histories |
| B3 | DSMC | 0.5 m cube, He, Kn ≈ 1, Δx = 0.05 m, Δt = 2 µs, 30 particles/cell | 200 + 1000 steps |
| B4 | DSMC | satellite, O/N2/O2 (rotation, vibration), Kn ≈ 0.5, Δx = 0.1 m | 200 + 600 steps |

The configurations are generated by the script (fixed seeds) and cover the
dominant work types: BVH traversal with few or many triangles (B1, B2), and
the DSMC time step with monatomic gas and with internal energy (B3, B4).

```bash
python3 scripts/benchmark.py run build/<preset>/vleo_solver <label> [--repeat 3] [--cases B1 B3]
python3 scripts/benchmark.py compare results/<before>.json results/<after>.json
```

Each case is run `--repeat` times; the median wall time is reported together
with the throughput (histories/s, DSMC particle steps/s), the phase profile
(`--profile`: each phase is fenced, so the sum is the wall time of the
measured loop) and the **efficiency** SE(C_D)² · wall time (time for a given
statistical accuracy; lower is better, independent of the run length).

## Method for before/after comparisons (M5.4)

The development laptop is not quiet (desktop load average 7–11), so
sequential runs fluctuate by up to ±15 %. The final comparison therefore
uses a separate build of the M4 state (commit `27b4990`, `git worktree`) and
the M5 build, run directly after each other, three repetitions each, median.
Repetitions of one build agree within 1 % on the GPU and 3–9 % on the CPU.
After every optimisation step the complete test suite was run and
`C_D` was compared: **all results are bitwise identical** to the M4 build
(same seed and backend, z = 0.0 in every row below).

## Baseline profiles (M5.2, before optimisation)

Share of the phase time (`baseline-*.json`):

| Case | CPU (OpenMP) | GPU (gfx1103) |
| ---- | ------------ | ------------- |
| B1 | transport 51 %, inject 38 %, moments 10 % | transport 60 %, inject 37 % |
| B2 | transport 85 %, inject 12 % | transport 85 %, inject 13 % |
| B3 | **compact 27 %**, move 22 %, sort 12 %, step reduce 12 %, collide 12 % | move 45 %, collide 20 %, step reduce 16 %, compact 7 %, sort 7 % |
| B4 | **compact 27 %**, move 24 %, collide 15 %, step reduce 10 %, histogram 8 % | move 44 %, collide 34 %, step reduce 9 %, compact 6 % |

Dominant kernels: TPMC – BVH transport (and, for small meshes, injection);
DSMC – particle compaction on the CPU, the move kernel (transport with
surface interactions) and collisions on the GPU.

## Optimisations (M5.3, M5.5)

| Step | Change | Effect | Kept |
| ---- | ------ | ------ | ---- |
| opt1 | DSMC: lazy compaction – ended particles stay as `Free` slots until more than 5 % of the storage is free; non-active particles skip binning | CPU B3/B4: compaction share 27 % → ~3 % | yes |
| opt2 | DSMC: cell sort compares storage indices instead of loading particle ids (ids grow with the index, invariant tested in `test_grid`) | CPU sort −30 % | yes |
| opt3 | DSMC: non-sampling steps reduce only status counts and interactions (one reduction instead of the full moment set); value count = actual species | step reduce −40 % | yes |
| opt3 | TPMC: fused inject + transport kernel (no particle arrays written between the two) | CPU B1 +8 %; **GPU slower** (register pressure, −10 %) | host backends only |
| opt4 (M5.5) | BVH node boxes in single precision (outward-rounded with `nextafter` and padded by 1e-5 × geometry scale; ray–triangle tests stay in double) | GPU B2 +24 %; CPU −5 % | GPU backends only (`BvhReal`) |

Mixed precision (M5.5), error analysis: a float box is only used for culling.
The stored box contains the exact double box (padding ≥ 1e-5 · scale is
far larger than float rounding of ≤ 6e-8 · scale, plus outward rounding), so
no ray that hits a triangle in double precision can be culled: the closest hit
and the crossing count are exactly those of the double BVH. Verified by the
brute-force comparison tests in `test_ray`/`test_transport` on GPU and by
the bitwise identical benchmark results. Larger boxes only cost extra node
visits, which is the reason for the slowdown on CPUs (no gain from float
loads there).

## Result: M4 → M5 (median of 3, interleaved builds, 2026-11-13)

CPU, `cpu-release`, 12 threads (`ab-base-cpu.json` → `ab-m5-cpu.json`):

| Case | M4 [s] | M5 [s] | Throughput M5 | Speed-up | C_D (identical) |
| ---- | ------ | ------ | ------------- | -------- | --------------- |
| B1 | 1.80 | 1.64 | 1.22·10⁷ histories/s | 1.10× | 4.95440 |
| B2 | 3.29 | 2.91 | 3.44·10⁶ histories/s | 1.13× | 1.65450 |
| B3 | 15.32 | 11.71 | 1.85·10⁷ particle steps/s | 1.31× | 0.71228 |
| B4 | 20.42 | 16.51 | 1.74·10⁷ particle steps/s | 1.24× | 4.61274 |

GPU, `hip-gfx1103`, Radeon 740M (`ab-base-hip-gfx1103.json` → `ab-m5-hip-gfx1103.json`):

| Case | M4 [s] | M5 [s] | Throughput M5 | Speed-up | C_D (identical) |
| ---- | ------ | ------ | ------------- | -------- | --------------- |
| B1 | 3.96 | 3.88 | 5.16·10⁶ histories/s | 1.02× | 4.95440 |
| B2 | 5.54 | 3.86 | 2.59·10⁶ histories/s | 1.44× | 1.65450 |
| B3 | 17.41 | 16.59 | 1.31·10⁷ particle steps/s | 1.05× | 0.71246 |
| B4 | 30.30 | 26.17 | 1.10·10⁷ particle steps/s | 1.16× | 4.61486 |

The M5 runs include `--profile` (fences after every phase), so the M5 times
are slightly pessimistic. In quiet conditions, single CPU runs reached up to
2.0× (B3) and 1.7× (B4), because the M4 compaction cost grows with
memory-bandwidth contention. The CPU and GPU C_D differ in the last digits
because floating-point rounding (device math, reduction order) changes
individual DSMC collisions; TPMC is identical across backends.

Profiles after M5: the GPU DSMC step is dominated by the move kernel
(45–53 %) and collisions (20–39 %); on the CPU by move (41–47 %). Further
work (not done): per-cell particle reordering for coalesced access in the
move/collide kernels, and a shared-memory traversal stack for the BVH.

The intermediate files `opt1-cpu` … `opt4-*` are the sequential
measurements of the individual steps (noisy, see above).
